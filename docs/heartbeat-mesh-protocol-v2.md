# 分布式心跳矩阵协议 V2

## 目标

每台 Ubuntu 主机运行独立 Agent，保存成员表、各节点最后心跳和邻居同步水位。所有节点主动上报，主服务只读取多个 Agent 的视角并形成页面样本。

网络、应用和资源状态均由对应宿主机采集。CCNODE 负责读取与合并报告，不代替目标节点执行测试。

## 参数

| 参数 | 默认值 | 说明 |
|---|---:|---|
| 心跳新鲜期 | 300 秒 | 自身心跳和外部可见租约有效期 |
| 单目标间隔 | 300 秒 | 同一目标的正常上报冷却 |
| 单轮扇出 | 3 | 每分钟最多选择三个到期邻居 |
| 启动尝试上限 | 5 | 未取得外部确认时一轮的目标上限 |
| 调度 | 60 秒，加 0 到 30 秒抖动 | 分散同时请求 |
| 请求超时 | 4 秒 | 单目标网络超时 |
| 单轮预算 | 20 秒 | 到达预算后停止本轮 |
| 增量批次 | 64 条 | POST 单方向记录上限 |
| 见证 ID | 8 个 | `seen_by` 上限 |
| HTTP 正文 | 512 KiB | 请求和响应硬限制 |
| HTTP 并发 | 32 | 单 Agent 工作线程上限 |
| 主服务报告源 | 3 | 每分钟合并的成功视角数 |
| 主服务尝试 | 6 | 每分钟候选尝试上限 |
| 离线窗口 | 660 秒 | 两次上报周期和调度余量 |

## 本地状态

Agent 使用 SQLite WAL：

- `registered_nodes` 保存地址、`membership_status` 和 `membership_version`。
- `heartbeat_records` 保存每个活动节点最后一次已接受心跳。
- `outbound_status` 保存尝试结果、失败次数、下次尝试、记录水位和成员摘要。
- `seen_reports` 保存 30 分钟内的 `report_id`，并按接收时间建立索引。
- `local_meta` 保存本机启动代次、心跳序号和已应用部署纪元。

数据库迁移使用 `BEGIN IMMEDIATE` 串行执行。V1 数据库原位增加字段和索引，已有记录继续保留。

## 成员版本

部署脚本为同一轮部署生成统一的 `membership_epoch`。Agent 第一次应用更高纪元时，把本地成员表中未出现在新快照内的活动节点标记为 `retired`。

成员合并规则：

1. 更高版本覆盖更低版本。
2. 相同版本冲突时，失效墓碑优先。
3. 旧配置、旧注册表和旧心跳无法恢复已失效成员。
4. 重新启用节点需要使用更高部署纪元。

节点标记失效后应执行一次 `--all-ubuntu` 部署，使持有旧成员记录的活动节点生成墓碑并传播。

## 心跳版本

V2 心跳版本为：

```text
(incarnation, sequence, observed_at)
```

`incarnation` 在 Agent 服务启动时递增，`sequence` 在当前启动代次内递增，`observed_at` 用于新鲜度判断。两个 V2 记录先比较启动代次和序号。滚动升级期间，只要一侧属于 V1，就按观察时间兼容比较。

该模型可处理服务重启、时钟回拨和重复转发。旧序号无法覆盖新序号，更高启动代次可以接替上一次运行状态。

## 目标选择

启动或最近 300 秒没有任何邻居确认时，节点随机尝试当前不在退避期的邻居。一轮最多 5 个目标，收到第一个有效确认后结束。

存在有效确认时，每分钟执行一次目标选择，同一目标保持 300 秒冷却。每轮最多选择：

- 两个由 `SHA256(self_id:peer_id)` 排名确定的稳定邻居。
- 一个从到期目标中选择的随机邻居。

稳定邻居在冷却到期时优先进入本轮，随机到期邻居填充剩余名额。节点数量较少时目标数自然收缩。失效成员和处于退避期的邻居不参与选择。节点间连接数从全连接模型的每轮 `N × (N - 1)` 降为每分钟最多 `3N`。

## 增量同步

连接由发送方主动建立。一次 HTTP 交换同时完成请求和响应两个方向的数据补齐。

V2 请求携带：

- `report_id`、`sender_id` 和 `sent_at`。
- 发送方自身心跳，以及目标尚未确认的记录，最多 64 条。
- 发送方 `known_versions` 和 `membership_digest`。
- 成员摘要不一致时携带完整 `registry`。

V2 响应携带接收方自身心跳、发送方缺少的记录、接收方版本水位和成员摘要。摘要不一致时返回完整成员表。

响应只保留一份 `records`。V1 中重复的 `self`、`latest_records`、`received` 和 `outbound` 不进入 V2 响应。首次同步超过 64 条时，后续交换依据新水位继续补齐。

## 去重与防循环

- 邻居版本水位阻止相同记录在相同方向重复发送。
- 接收端只接受更高版本，相同版本只合并见证信息。
- 相同 `report_id` 在 30 分钟内只处理一次。
- `seen_by` 最多保存 8 个 ID，`seen_count` 保留已知见证数量。
- 超过 300 秒的最后记录只在目标缺失时做一次反熵补齐。
- 成员墓碑阻止已失效节点通过旧状态重新加入。

## 失败控制

目标失败后按 5、10、20、40、80、160、300 秒退避。成功后失败计数归零，并恢复 300 秒单目标冷却。

正常周期最多连接 3 个目标，注册周期最多尝试 5 个目标，单目标超时 4 秒，单轮预算 20 秒，systemd oneshot 超时 30 秒。

Agent 的监听队列为 128，工作线程上限为 32。并发满时关闭新连接，发送端随后按退避规则重试。

## 主服务采样

主服务每 60 秒随机排列活动节点，从最多 6 个候选中收集 3 个签名有效的 V2 紧凑报告。每个受管节点从三个视角中选择版本最新的心跳，并合并活动成员表。

每轮采样单独写入 `mesh_poll_cycles`，记录尝试数、成功报告源、来源节点和错误。采集器状态与节点状态严格分离：

- 至少取得一个有效报告时，才为节点生成本轮健康样本。
- 所有候选报告源均失败时，只写入 `failed` 采集周期，不生成任何节点离线样本。
- 页面沿用各节点最后一个可信样本，并在共同时间轴上用灰色虚线标记采集异常，曲线在该分钟断开。
- V2 上线前遗留的“零来源且全部节点为 0”样本在读取历史时自动识别为采集异常，不参与节点曲线。

状态规则：

- 多节点环境中的 self-only 心跳网络活性为 0。
- 至少一个外部见证且心跳不足 300 秒时，网络活性为 100。
- 心跳达到 300 秒且不足 660 秒时，网络活性为 70。
- 心跳达到 660 秒时判定离线。
- `app_score` 由对应节点本机检查自定义 systemd 服务计算。

三个视角降低单个 Agent 局部缺失造成误报的概率。网络完全分区时，各连通分量只能依据本地持有的最后版本形成结论。

页面保留 100、70、0 三档状态用于在线、同步延迟和离线分类，同时计算连续的 `network_trend_score` 用于曲线和百分比显示：

```text
network_trend_score = 75% × freshness_score + 25% × visibility_score
```

`freshness_score` 在心跳 0 到 300 秒之间从 100 线性降到 70，在 300 到 660 秒之间从 70 线性降到 0。`visibility_score` 为 `peer_visible / peer_expected`。因此心跳年龄和同伴可见率不同的节点会形成不同曲线，原始状态边界保持不变。

## 规模边界

- 节点连接次数为每分钟最多 `3N`，同一目标至少间隔 5 分钟，随节点数线性增长。
- `known_versions` 是 O(N) 摘要，节点间总字节量上界为 O(N²)。
- 心跳正文按变化量发送，稳定期通常只有发送方自身记录。
- 主服务每分钟读取 3 份 O(N) 紧凑快照。
- 自动化测试以 150 个节点、每节点 7 个服务验证 GET 和 POST 均低于 512 KiB。

正文达到 512 KiB 时服务端返回 507。客户端明确记录大小错误，不会继续处理截断正文。

## V1 滚动兼容

- V2 Agent 接受 V1 `POST /v1/heartbeat`。
- 未声明版本的 `GET /v1/report` 返回 V1 结构。
- `X-Heartbeat-Protocol: 2` 请求返回 V2 紧凑结构。
- V2 发往 V1 Agent 的额外字段会被旧实现忽略，V2 发送方仍可合并 V1 响应。

## 安全与确认

- POST、GET 和响应均使用 HMAC-SHA256。
- 客户端验证响应节点 ID、时间戳、正文长度和正文签名。
- 发送方自身心跳必须不足 300 秒，并在接收端实际写入后才返回 `ok=true`。
- 请求允许 650 秒主机时钟偏差。
- 配置权限为 `0640 root:serverdesk-heartbeat`。
- UFW 只放行成员来源 IP，云厂商安全组需配置同一来源白名单。

## 验收项

1. 每分钟调度轮最多选择三个到期邻居，稳定邻居到期时优先。
2. 注册周期最多尝试 5 个邻居，首次成功后结束。
3. 失败目标执行指数退避，单轮受时间预算限制。
4. 相同版本的墓碑无法被活动记录覆盖。
5. 旧序号无法覆盖新序号。
6. 已确认记录不会向同一邻居重复发送。
7. `seen_by` 不超过 8 个 ID。
8. 陈旧发送方心跳不会获得成功确认。
9. 主服务每轮合并 3 个成功视角。
10. 150 节点规模载荷低于 512 KiB。
11. V1 POST 和 V1 GET 在滚动升级期间可用。
12. 零个成功报告源只生成采集失败周期，不生成节点离线样本。
13. 历史零来源误报显示为灰色采集异常标记，节点曲线在该分钟断开。
14. 网络趋势同时反映心跳年龄和同伴可见率。
