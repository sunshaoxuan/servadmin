# CCNODE-MAIN 心跳波动原因分析

## 结论

强烈波动由 CCNODE-MAIN 的主动上报定时器在系统重启后停止调度引起。Agent 接收服务持续在线，主服务采集也持续成功。页面交替显示 0/7 与非零传播值，是不同报告源对同一心跳版本持有不同见证集合造成的锯齿。

## 排除项

- 主服务整体采集中断：三小时内 165 个周期全部成功。
- 全网同时中断：另外 7 台节点同一窗口没有未确认样本。
- CCNODE Agent 反复重启：Agent 从新 boot 后持续运行，`NRestarts=0`。
- 应用服务整体故障：心跳记录中的应用分持续为 100。

## 数据如何形成锯齿

1. 主服务或邻居读取 CCNODE 的 Agent，Agent 生成新的本机版本。
2. 主动上报停止后，本机新版本通常只有 CCNODE 自身见证。
3. 邻居向 CCNODE 上报时收到该版本，并在本地合并时加入自己的节点 ID。
4. 邻居之间传播后，同一版本可能积累多个见证。
5. 主服务每分钟读取随机报告源，并按心跳版本选择候选。直接来源可能返回仅自见记录，邻居来源可能返回带见证记录。
6. 页面在 0/7 与 1/7 至 5/7 之间切换。

## 重启来源边界

客机证据确认发生过一次缺少正常关机序列的重启。现有日志没有 kernel panic、OOM、watchdog 或 unattended-upgrades 自动重启记录。宿主机故障、供应商维护、硬复位和外部电源事件无法仅凭客机日志区分，需要供应商控制台事件记录作为下一层证据。

## 建议修复顺序

第一步应恢复 CCNODE-MAIN 的主动上报 timer，并确认状态从 `active / elapsed` 变为 `active / waiting`，最近触发持续更新。随后观察至少 10 个采样周期的邻居确认率。

长期应将 timer 的首次调度改为相对 timer 激活时间触发，并为 `active / elapsed`、最近触发过旧、下一触发为空建立独立告警。全面体检已经加入该检查项。
